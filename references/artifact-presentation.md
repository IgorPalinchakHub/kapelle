# Human artifact presentation contract

Human artifacts optimize for review and later maintenance, not for carrying runtime metadata.

## Common structure

Put the most useful information first:

1. short summary;
2. current scope or behavior;
3. key decisions and constraints;
4. unresolved questions, blockers, or deferrals;
5. links to detailed contracts and ADRs.

Do not place fingerprints, agent routing, execution logs, schema internals, or stage handoff blocks
inside `proposal.md`, `spec.md`, `design.md`, `tasks.md`, or `test-plan.md`.

## Documents

- `STATUS.md`: generated entry point, normally at most 100 lines.
- `proposal.md`: problem, goal, scope, non-goals, impact, risks, and product decisions.
- `spec.md`: observable behavior, actors, requirements, ACs, edge cases, constraints, compatibility.
- `design.md`: affected components, boundaries, flows, contracts, data, security, decisions, ADRs,
  validation, and as-built deviations.
- `tasks.md`: workstream checklist with task id, outcome, meaningful dependency, AC coverage,
  blocker, and validation state.
- `test-plan.md`: strategy, AC/integration coverage, required/optional commands, manual checks,
  explicit skips, and deferrals.

For medium features, prefer 3–7 workstreams and 7–15 implementation tasks. These are review
signals, not correctness limits.

## Generated status

`STATUS.md` begins with:

```md
<!-- generated by Kapelle; do not edit -->
```

It is rebuilt from `_kapelle/state.json` and human documents. Manual drift is an error; edit the
source artifact or state evidence and rebuild.

## Task checklist

Checkboxes are human claims:

- `[ ]` means not confirmed complete;
- `[x]` means implemented according to the document author;
- validation state comes from current `_kapelle/validation/` evidence, not from the checkbox.

After recovery with no durable validation evidence, `[x]` maps to
`implemented-unverified`.

## Documentation convergence

Before feature review, reconcile:

```text
proposal <-> final scope
spec <-> observable implementation
design <-> technical implementation
contracts <-> providers and consumers
tasks <-> implemented work
test-plan <-> performed validation
ADR <-> actual architectural decisions
```

The machine verdict is `_kapelle/reviews/documentation-convergence.json`. Feature review and ship
require a current `PASS`; it is current only while both complete input fingerprints and the
reviewed implementation-file fingerprints match. Observable requirement changes still use the
change lifecycle.
